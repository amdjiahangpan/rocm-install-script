# ROCm 7.14.0 Multi-GFX Installer Design

Date: 2026-07-30
Status: Approved

## Purpose

`rocm-install.sh` must support hosts that expose more than one unique AMD GPU
architecture. The motivating system combines a Ryzen AI Max+ 395 integrated
GPU (`gfx1151`) with a Radeon AI PRO R9700 discrete GPU (`gfx1201`). Both GPUs
must be usable after one installer run.

The existing single-GFX behavior remains valid. Multi-GFX support changes GPU
selection and artifact composition only; it does not change the supported ROCm
release, operating systems, kernel policy, driver policy, SSH setup, reboot
policy, or uninstall scope.

## Selected Approach

The installer uses one normalized set of requested architectures and one
install plan for the whole host. It does not create and execute an independent
installation plan per GPU, and it does not install every architecture when the
host only needs a subset.

The normalized set has these properties:

- every value is a supported `gfx` key from the embedded ROCm 7.14 artifact
  table;
- duplicate values are removed;
- values are sorted for deterministic plans, commands, and tests;
- an empty set is invalid;
- one unsupported value invalidates the entire set before system mutation.

For the motivating host, the normalized set is:

```text
gfx1151 gfx1201
```

## GPU Discovery and Overrides

Automatic discovery continues to scan KFD topology nodes with
`cpu_cores_count == 0` and a nonzero `gfx_target_version`. It decodes every GPU
node, deduplicates the results, and returns all unique architectures instead of
requiring exactly one.

`--gpu-arch` becomes repeatable:

```bash
sudo bash ./rocm-install.sh \
  --gpu-arch gfx1151 \
  --gpu-arch gfx1201
```

One occurrence preserves the existing CLI behavior. When at least one
`--gpu-arch` is present, the complete explicit set replaces automatic KFD
discovery; explicit and detected values are never merged. Repeated identical
arguments are accepted and deduplicated.

An explicit override expresses requested artifact coverage. It is not required
to match the currently visible KFD topology, which preserves recovery and
pre-provisioning use cases. Post-install verification still requires every
requested architecture to be visible unless verification is deferred because
the current run requires a reboot.

## Product Names

DRM product names remain informational and never select artifacts, drivers, or
kernels. The installer collects all unique nonempty names found through sysfs
or exact `amdgpu.ids` lookup and displays them in deterministic order.

The installer does not infer a relationship between a KFD topology node and a
DRM card. Associating a marketing name with a specific `gfx` target would
require topology correlation that the current input contract does not provide
reliably.

## Install Plan Representation

The scalar GPU and artifact fields become normalized collections. Internally,
collection values use newline-delimited records so shell word splitting cannot
alter entries. User-facing output renders them as comma-separated values.

The required plan keys are:

```text
gfxes os_key repo_slug method artifacts driver_mode
```

`product_names` is optional and informational. A plan for the motivating host
using APT renders as:

```text
INSTALL PLAN
gfx=gfx1151,gfx1201
os=ubuntu-26.04
method=apt
artifact=amdrocm-core-sdk7.14-gfx1151,amdrocm-core-sdk7.14-gfx1201
driver_mode=inbox
```

Plan validation reconstructs the expected artifacts from the normalized GFX
set and selected method. The stored and reconstructed values must match
exactly. No package, repository, driver, or system command runs before this
validation succeeds and interactive confirmation is obtained.

## Artifact Composition

### APT

APT resolves one architecture-specific full Core SDK package per GFX target:

```text
amdrocm-core-sdk7.14-gfx1151
amdrocm-core-sdk7.14-gfx1201
```

All resolved packages are passed to one `apt-get install` transaction. Their
architecture-neutral dependencies are shared by normal Debian package
resolution. The installer does not run one APT transaction per GPU.

### Pip

Pip resolves one PEP 508 requirement containing every device extra:

```text
rocm[libraries,device-gfx1151,device-gfx1201]==7.14.0
```

The requirement is installed once into the existing fixed virtual environment.
This installs one shared core and libraries package plus one device package for
each requested architecture.

### Tarball

One GFX target continues to use its reviewed architecture-specific tarball.
More than one unique GFX target uses the official full multi-architecture
artifact:

```text
therock-dist-linux-multiarch-7.14.0.tar.gz
```

The installer never overlays two architecture-specific or family-specific
tarballs. Such an overlay could replace shared binaries, libraries, manifests,
or metadata and is not a supported ROCm distribution contract.

The multi-architecture artifact is an explicit ROCm 7.14 record, not a generic
fallback for unknown targets. Every requested GFX must still pass the supported
architecture table before this artifact is selected.

## Installation and Uninstall

The APT installer consumes the complete package collection as one safely quoted
argument array. Pip and tarball each consume their one composed artifact.
Existing legacy ROCm migration runs once before the current installation.

Uninstall behavior does not need a new selection model. It already enumerates
all supported architecture-specific APT package candidates and purges only
those that are installed. Fixed pip and tarball roots remain single directories
and are removed as before.

## Post-Install Verification

When verification is not deferred for a required reboot, the installer:

1. invokes the selected installation root's `rocminfo`;
2. extracts all visible `gfx` agent names from its output;
3. confirms that every requested plan GFX is present;
4. permits additional visible architectures;
5. retains the existing `amd-smi version` check for ROCm 7.14.0.

Missing any requested GFX makes verification fail. Nonempty `rocminfo` output
alone is no longer sufficient.

Pip verification additionally uses the installed environment's ROCm tooling as
already selected by the method-specific root. Package-level tests assert that
the composed requirement contains every requested device extra. A workload
kernel-launch test remains outside this installer's system-configuration scope.

## Failure Policy

The installer fails before mutation when:

- automatic discovery finds no GPU architecture;
- an explicit override set is empty;
- any detected or explicit GFX is unsupported;
- artifact composition fails for any requested GFX;
- the plan contains duplicate, unsorted, missing, or unexpected collection
  values;
- multi-GFX tarball mode cannot resolve the reviewed full multi-architecture
  artifact.

It never silently drops an unsupported GPU and never falls back to installing
only one member of a multi-GFX host.

## Test Boundary

The shell suite adds coverage for:

- automatic KFD discovery of `gfx1151` and `gfx1201`;
- deterministic sorting and duplicate removal;
- failure when one member of a detected or explicit set is unsupported;
- one and repeated `--gpu-arch` arguments;
- explicit overrides replacing rather than extending automatic detection;
- multiple informational DRM product names;
- exact multi-GFX plan validation and rendering;
- one APT transaction containing both SDK packages;
- one pip requirement containing both device extras;
- full multi-architecture tarball selection for multiple GFX targets;
- retained architecture-specific tarball selection for one target;
- successful verification when all requested GFX agents are visible;
- failed verification when either requested GFX is missing;
- unchanged single-GFX lifecycle behavior.

Tests continue to source the installer in library mode and replace command and
filesystem mutations. The observed `aup-395-23` fixture remains the single-GFX
regression fixture; a synthetic heterogeneous KFD/DRM fixture represents the
`gfx1151` plus `gfx1201` host.

## Documentation Changes

The README will describe automatic multi-GFX discovery, repeatable
`--gpu-arch`, method-specific artifact composition, multi-GFX plan output, and
verification semantics. Its examples will include the Ryzen AI Max+ 395 plus
Radeon AI PRO R9700 configuration.

The previous ROCm 7.14 installer design remains the baseline. This document
supersedes only its single-GFX selection, artifact, and verification rules.
