# ROCm 7.14 Installer Repair Design

## Goal

Make `rocm-install.sh` safely install and repeatedly manage ROCm 7.14.0 across the reviewed Ubuntu/GPU combinations, including recovery when the current driver cannot create KFD topology.

The implementation lives on branch `ROCm_7.14.0` and retains a single production script.

## Evidence

The NV20 test host established these facts:

- The running host is Ubuntu 24.04.2 with kernel `6.8.0-138-generic`.
- The GPU is RX 9060 XT, PCI ID `1002:7590`, and the official GFX target is `gfx1200`.
- The Ubuntu 6.8 inbox driver failed probe with `-22`; KFD exposed only a CPU node.
- AMDGPU 31.40 DKMS loaded successfully on the same 6.8 kernel and created a KFD GPU node with `gfx_target_version 120000`.
- The real 31.40 packages use versions `1:6.19.14.31400000-*` and `1:31.40.0.0.31400000-*`; DKMS reports `amdgpu/6.19.14-*`.
- The current script misclassifies that valid installation as dirty, resolves `auto` to inbox, and can repeatedly reinstall or remove the required driver.
- A host with both 6.8 GA and 7.0 HWE kernels needs an explicit bootloader selection; installing a metapackage and rebooting does not guarantee the target kernel runs.

## Selected architecture

Use one state-machine-style `rocm-install.sh` with four layers:

1. Detection collects facts and performs no mutation.
2. Policy maps reviewed facts to a supported configuration.
3. Planning computes exact actions and renders them before confirmation.
4. Execution applies the approved actions and re-detects state after every stage.

No compatibility shim retains the old unconditional kernel installation or immediate reboot behavior.

## Detection

### Host

Record the real values from `/etc/os-release`, the running kernel release, CPU architecture, boot ID, installed kernel images, and bootloader capabilities.

Do not render every Ubuntu `VERSION_ID=24.04` host as Ubuntu 24.04.4. Policy support is determined from the reviewed base release plus the required kernel/package state; rendered output preserves the detected release description.

### GPU

Use two independent sources:

- Primary: KFD topology nodes with `cpu_cores_count == 0` and nonzero `gfx_target_version`.
- Recovery: AMD PCI device/revision records resolved through a reviewed `PCI_GPU_DATA` table.

Each PCI record contains the PCI device, optional revision constraint, GFX target, and device class (`ryzen`, `radeon`, or `instinct`). The table includes RX 9060 XT `1002:7590 -> gfx1200, radeon`.

When both KFD and PCI are available, the complete normalized GFX sets must agree. A disagreement fails closed. Product names remain informational and never select an artifact.

An unknown PCI ID fails with the detected ID and an exact `--gpu-arch` recovery command template; it is never inferred from a marketing name.

### Driver

Collect:

- installed `amdgpu-dkms` Debian version;
- installed `amdgpu-dkms-firmware` Debian version;
- all AMDGPU DKMS status records and target kernels;
- the module selected by `modinfo` for the running kernel;
- the PCI driver binding and KFD availability.

A clean 31.40 installation is recognized from real package metadata, not the literal text `31.40` in the DKMS module version. The driver package, firmware package, source/build identity, installed DKMS records, and required target kernels must be mutually consistent.

## Policy

Keep reviewed data tables in the production script:

- `GPU_POLICY_DATA`: GFX, class, artifact records, and default driver policy.
- `PCI_GPU_DATA`: PCI device/revision to GFX and class.
- `HOST_POLICY_DATA`: host release, GPU class, driver mode, target kernel release/flavor, and metapackage.

`auto` becomes context-sensitive:

- Ryzen paths use the reviewed inbox-driver policy.
- Radeon and Instinct paths use the reviewed AMDGPU driver policy; Ubuntu 24.04 RDNA4, including gfx1200/gfx1201, resolves to DKMS 31.40.

Explicit driver modes are accepted only when the host/GPU matrix permits them. Unsupported combinations fail before mutation. A newer numeric kernel is not automatically considered compatible.

## Install plan

`resolve_install_plan` is pure with respect to system mutation. The rendered plan includes:

- detected OS description and policy key;
- GFX set and detection source (`kfd`, `pci`, or explicit);
- GPU class;
- current and target driver state;
- current kernel, target kernel, target metapackage, and kernel status;
- exact ROCm artifacts;
- ordered actions.

The plan is validated again immediately before execution. Each completed stage re-runs the relevant detector instead of trusting stale plan fields.

A repeated run over a clean host performs no kernel, driver, or ROCm reinstall.

## Kernel state machine

### Default behavior

A kernel mismatch prints the current release, required release/flavor, metapackage, installed matching images, policy reason, and next command. It exits nonzero without installing a kernel or rebooting.

### Explicit preparation

`--prepare-kernel` allows installation of the reviewed metapackage. After installation the script verifies the package and exact boot image, prints the required boot action, and stops.

### Explicit reboot automation

`--reboot-after-kernel` is valid only with `--prepare-kernel`.

Before reboot, the script must:

1. identify a supported bootloader;
2. resolve the exact target boot entry;
3. configure a one-shot next boot;
4. verify the configured entry;
5. write `/var/lib/rocm-installer/pending-kernel` atomically;
6. print current/target kernels and obtain a second confirmation.

The pending record contains the target release/flavor, selected boot entry, pre-reboot boot ID, and attempt count.

On the next run:

- matching kernel: remove the pending record and continue;
- changed boot ID but mismatched kernel: mark the attempt failed, print manual boot instructions, and never reboot automatically again;
- unchanged boot ID: report that the reboot has not occurred and stop.

Non-interactive reboot requires both explicit kernel flags. There is no implicit immediate reboot path.

## Errors and exit semantics

Every failing stage prints the stage, detected evidence, required state, and next safe action.

Stable distinct nonzero statuses cover:

- unsupported host policy;
- explicit GPU input error;
- kernel action required;
- reboot pending or failed;
- driver migration failure;
- installation or verification failure.

Exit zero means the requested operation completed. `--skip-reboot` cannot report success when ROCm installation was deferred before the driver or ROCm stages.

## CLI changes

Add:

- `--prepare-kernel`
- `--reboot-after-kernel`

Retain `--skip-reboot` only for post-driver/group/udev reboot suppression. It does not override the kernel state machine.

Update help and README examples to show strict default behavior and explicit automation.

## Validation

### Automated

Add behavior tests for:

- PCI `1002:7590 -> gfx1200, radeon`;
- KFD `120000 -> gfx1200`;
- KFD/PCI agreement and disagreement;
- unknown PCI recovery error;
- Ubuntu 24.04 gfx1200 `auto -> dkms`;
- real 31.40 package/firmware/DKMS version formats;
- clean driver idempotence with no purge, reinstall, or reboot;
- partial or inconsistent driver migration;
- default kernel mismatch with no mutation;
- explicit one-shot kernel preparation and reboot;
- second boot mismatch with no second reboot;
- successful pending-state completion;
- exact messages and exit statuses.

Run the complete existing shell suite after focused tests.

### NV20

Deploy the branch script without replacing the user's source copy. Run:

1. read-only preflight;
2. automatic PCI/KFD agreement and `gfx1200` resolution;
3. DKMS 31.40 idempotence check;
4. ROCm 7.14.0 APT installation with `--skip-ssh` and no automatic reboot;
5. reboot only when required and reconnect;
6. `rocminfo`, `amd-smi version`, and a minimal HIP workload.

Only exercised paths may be reported as verified.

## Non-goals

- Guessing GFX from marketing names.
- Automatically accepting newer unqualified kernels.
- Supporting Ubuntu 20.04.
- Retaining the old immediate-reboot behavior.
- Splitting the installer into multiple production scripts.
